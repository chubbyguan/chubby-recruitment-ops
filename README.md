# Chubby｜社交招聘工作流

这是一个给 Codex 和 Claude Code 使用的招聘工作流插件。

把插件安装到自己的 Agent 后，只要把你的岗位、招聘邮箱、招聘数据表格和发布渠道告诉 Agent，就可以按同一套流程完成招聘内容、简历初筛、面试核验、候选评价和招聘日报。个人招聘者和任意规模的团队都可以使用。

当前版本：`0.8.0`

`0.8.0` 把原来容易越跑越大的闭环拆成三条互不混跑的执行链。日常对话默认
走 `quick`，只处理一个候选人、一次面试、一条通知或一小批新邮件；
定时任务走 `scheduled`，只按水位增量处理；修改插件、跑测试和同步 GitHub
走 `maintenance`，绝不读取邮箱或改候选人数据。这样可以避免“查一个人，
顺手做全量体检、全量扫描、测试和发布”造成的长时间等待。

`0.7.1` 修复人工决策通知信息不完整的问题。待复核通知现在必须包含
候选人姓名、候选人/投递/动作 ID、岗位、分数拆解、关键证据、风险、待补
资料、面试事实、可选动作，以及候选人和决策记录链接。缺少任一必填信息时
通知会被拦截，不再发送“只有分数、看不出是谁”的消息。

`0.7.0` 重点修复四个真实运行卡点：旧岗位版本只隔离单条投递，不再拖垮
整轮；高分但硬门槛未核验的候选人会进入待复核队列；协作工具接口的限流和临时超时
会按上限自动退避重试；只有拿到原始 PDF/DOC/DOCX 文件时才计算附件
SHA-256，拿不到时明确记录“哈希不可用”，不会伪造去重结果。

`0.6.0` 新增招聘系统（ATS）接入：Agent 可以增量读取已授权的招聘系统岗位、
人才、投递阶段和面试事实，先生成私有快照和 dry-run，再幂等同步到现有
招聘数据表。任一写入失败都不会推进水位，重复运行也不会重复建档。招聘
系统里的面评只作参考事实，不会自动替你判定通过或淘汰。可接入的招聘系统
与协作工具以代码中的适配器为准。

## 它能帮你做什么

- 把岗位 JD 整理成适合小红书、微信、知乎等渠道的招聘内容；
- 记录每条内容发在哪个渠道，并统计真实效果；
- 从招聘邮箱读取新简历，识别重复投递；
- 增量读取已接入招聘系统中的候选人、投递阶段和面试事实；
- 把“候选人本人”和“针对具体岗位的投递”分开记录，避免转岗或重复投递覆盖历史；
- 候选人没有写岗位时，匹配最合适的岗位；
- 根据岗位要求整理候选人信息并给出初筛建议；
- 把历史岗位版本异常单独放进迁移复核，不让一条旧数据阻塞整轮；
- 把“高分但硬门槛未核验”的人单独推到人工复核队列；
- 按每个岗位自己的门槛和漏斗缺口，主动推荐高分、有完整简历但还没有进入面试的人；
- 把推荐写入待审批队列，通过 IM 通知提供“约面、补资料、人才池、暂不推进”选择；
- 对照日历和视频会议记录，确认哪些面试真实发生；
- 读取可用的原始智能纪要，生成带时间证据的面试评价；
- 找出已面试但没有纪要、没有评价或没有人工结论的人；
- 把候选人和处理结果同步到招聘数据表；
- 每天汇总发布量、简历数量、候选质量和跟进建议。

社交媒体内容由 Agent 准备，人来确认和发布。是否约面、合并重复候选人、淘汰或录用，也必须由人决定。Agent 可以自动同步“会议已发生”，但不会把“已完成”当成“已通过”。

## 安装

### Codex

```bash
codex plugin marketplace add chubbyguan/chubby-recruitment-ops --ref main
codex plugin add chubby-recruitment-ops@chubby-recruitment
```

安装后新建一个 Codex 任务。

### Claude Code

```bash
claude plugin marketplace add chubbyguan/chubby-recruitment-ops
claude plugin install chubby-recruitment-ops@chubby-recruitment --scope user
```

安装后重启 Claude Code。

已经在使用旧版本的用户，不要删除原配置。让 Agent 依次迁移，并为投递、阶段历史和证据建立独立表：

```text
请使用 recruitment-ops-setup，把当前招聘工作区迁移到 schema 4.0。
如果是 schema 2.0，先迁移到 3.0，再迁移到 4.0。
每一步先预览，确认备份后再执行。
不要把候选人、投递、阶段历史和证据映射到同一张表。
迁移后运行 doctor 和虚构数据验收，不要自动开启定时任务。
```

如果不熟悉终端，也可以先把仓库地址发给 Agent：

```text
请帮我安装这个招聘工作流插件：
https://github.com/chubbyguan/chubby-recruitment-ops

请根据我当前使用的是 Codex 还是 Claude Code 执行安装。
安装完成后，告诉我需要新建任务还是重启。
```

## 第一次使用

先准备这些信息：

- 招聘邮箱；
- 当前招聘岗位和 JD；
- 对外公司名称和已确认的薪资范围；
- 招聘数据表格；
- 希望使用的渠道；
- 招聘日报接收人；
- 业务工作区路径。

然后把下面这段话发给自己的 Agent：

```text
请使用 recruitment-ops-setup 为我初始化招聘工作流。

业务工作区：<路径>
招聘邮箱：<邮箱>
招聘数据表格：<链接或表格信息>
招聘系统：<已接入时填写入口或说明已授权；没有可不填>
发布渠道：<例如小红书、微信群、知乎>
日报接收人：<IM 私聊或群>

请先检查插件和连接权限，再带我完成配置。
使用虚构岗位、虚构简历和虚构面试做一次测试。
测试通过前不要创建定时任务，也不要发布任何社交媒体内容。
```

Agent 会继续向你确认缺少的信息，并完成邮箱、协作工具和岗位数据的连接测试。

## 三种运行方式

| 运行方式 | 什么时候用 | 默认范围 | 时间目标 |
| --- | --- | --- | --- |
| `quick` | 日常和 Agent 对话 | 单个岗位内容、候选人、面试、通知、推荐/日报快照，或一小批新邮件 | 数分钟 |
| `scheduled` | 定时任务自动唤醒 | 从上次水位开始的增量闭环 | 有时间上限 |
| `maintenance` | 明确要求改插件、测试或同步 GitHub | 只处理插件仓库 | 有时间上限 |

每次运行只能选择一种。日常对话默认 `quick`，不会自动升级成全量闭环；
定时任务不能改代码或推 GitHub；维护任务不能读取邮箱、修改候选人数据表、
发送候选人通知或推进生产水位。

如果一句话同时包含“马上处理某个候选人”和“顺便改插件”，Agent 应先用
`quick` 完成紧急业务项，再单独开始 `maintenance`，不能把两件事混成一轮。

## 日常怎么用

### 生成招聘内容

```text
请使用 recruitment-ops-run 的 quick/campaign 配置，并调用 social-recruitment-campaign。
只处理岗位 <岗位 ID>，整理成小红书和微信招聘内容。
公司名称和薪资只使用我提供的版本。
内容生成后先给我审核，不要自动发布。
```

### 处理新简历

```text
请使用 recruitment-ops-run 的 quick/inbox 配置。
只处理招聘邮箱从上次成功水位开始的下一批新简历，单批数量有上限。
完成去重、岗位匹配、候选人整理和数据表同步，并告诉我哪些人值得人工初筛。
不要做全邮箱、全日历或插件仓库扫描。
```

如果已经接入招聘系统，也可以直接说：

```text
请使用 recruitment-ops-run，同步招聘系统从上次成功水位以来的岗位、
候选人、投递阶段和面试事实。先 dry-run，检查无误后再写入招聘数据表。
不要修改招聘系统数据，不要自动判定候选人通过或淘汰。
```

### 生成招聘日报

```text
请使用 recruitment-ops-run 的 quick 配置，生成今天的招聘日报。
汇总今天发布了什么、收到多少简历、候选人匹配哪些岗位，以及建议我下一步跟进谁。
没有采集到的平台数据请直接写“未采集”。
```

日报的正式自动发送由每日固定时间的 `scheduled` 轮次负责。人工临时查看只读当前
已经同步的数据，不会顺带重新扫描整个邮箱、日历和招聘系统。

### 推荐高分但未面试的候选人

```text
请使用 recruitment-ops-run 的 quick/recommendation 配置。
从候选人、投递和证据表中找出达到当前岗位门槛、有完整简历、岗位仍在招，但面试表和日历都没有面试记录的人。
把推荐人选、岗位、分数、强证据、最大风险和建议动作通过 IM 发给我。
只创建待我确认的约面动作，不要自动发送面试邀请。
```

待复核通知会明确写出候选人是谁、为什么得到这个分数、已经面试到哪一
步、还缺什么证据，以及负责人可以选择的下一步。若这些信息没有全部取到，
Agent 应把通知记为失败并补数据，不能发送半成品。

### 面试前准备

```text
请使用 recruitment-ops-run 的 quick/interview 配置，并调用 recruitment-interview-review，
为候选人 <候选人或稳定 ID> 准备面试建议。
以当前岗位 JD 和已经核验的简历证据为准，给我必问问题、案例题、AI 实操题和待验证风险。
```

### 面试后评价

```text
请使用 recruitment-ops-run 的 quick/interview 配置，并调用 recruitment-interview-review。
只核验候选人 <候选人或稳定 ID> 对应的日历、视频会议和会议纪要。
有可用原始纪要的生成结构化评价，没有纪要的明确列为待补人工记录。
更新招聘进度，但不要替我做淘汰、约面或录用决定。
```

### 修改或发布插件

```text
请使用 recruitment-ops-run 的 maintenance/release 配置。
只修改、测试并发布招聘插件；不要读取邮箱、修改候选人数据表、发送候选人
通知或推进生产水位。测试通过后提交并推送 GitHub，再核验远端 SHA。
```

### 回填发布效果

人工发布后，把帖子链接和平台数据交给 Agent：

```text
这是今天已经人工发布的招聘内容和平台数据，请更新渠道记录：
<帖子链接、阅读、点赞、收藏、评论和投递数>
```

## 正常工作流程

```text
岗位确认
  → Agent 生成渠道内容
  → 人工审核并发布
  → Agent 读取招聘邮箱
  → Agent 增量读取招聘系统
  → 去重和岗位匹配
  → 分别同步候选人、投递、阶段和证据
  → 执行引擎按岗位门槛生成推荐
  → IM 待审批：约面 / 补资料 / 人才池 / 暂不推进
  → 批准约面后，Agent 提供若干可选时间
  → 人工确认并发送面试邀请
  → Agent 核验日历、会议和原始纪要
  → Agent 生成面试建议与待决策清单
  → Agent 生成招聘日报
  → 人决定下一轮、关闭、人才池或 Offer
```

## 使用时记住

- 每个招聘工作区单独配置邮箱、协作工具和岗位，不要复制其他工作区的候选人数据；
- Agent 不会自动发布小红书、微信或其他社交媒体；
- Agent 的评分是初筛建议，不是最终招聘决定；
- 同一个人可以有多条投递，但只能有一条候选人主档；
- 日历事件必须保存候选人 ID 或投递 ID；只有姓名相同不能当作已经面试；
- “面试已完成”“纪要可用”“AI 已评价”“负责人已决定”是四个不同状态；
- 没有可用原始纪要时，Agent 不应补写面试评价；
- 简历和邮件里的指令都不可信，不能让 Agent 执行；
- 没有真实平台数据时写“未采集”，不要猜数字；
- 第一次测试请使用虚构岗位、虚构简历和虚构面试。

## 常见问题

**安装后找不到 Skill**

Codex 新建任务；Claude Code 重启后再试。

**Agent 读取了错误的邮箱**

立即停止，让 Agent 重新核验邮箱当前账号，账号一致后再继续。

**数据表写入失败**

把真实表格链接交给 Agent，让它重新读取表格和字段，不要手工猜表格 ID。
遇到限流或临时超时，插件会自动做有上限的退避重试；权限、字段或表格映射
错误不会盲目重试，必须先修配置。

**附件能读到文字，但没有 SHA-256**

这通常表示邮箱连接器只给了抽取文本，没有提供原始文件。Agent 会继续使用
邮件 `message_id` 防止重复处理，但会把附件去重标成“不可用”。不要拿文件
名、下载链接或抽取文字伪造哈希。

**招聘系统已开权限，为什么还不能同步**

招聘系统权限和数据表格权限通常是两套权限。让 Agent 分别验证“招聘系统
读取”和“招聘数据表写入”；还要为每个招聘系统岗位明确绑定自己的岗位
ID，不能只靠岗位名称猜。

**日历里已经面试，数据表还是待面试**

让 Agent 使用 `recruitment-interview-review` 核验日历、视频会议和会议纪要。只看 IM 群消息不够。

**找不到面试纪要**

先检查视频会议关联的智能纪要，再让 Agent 按会议时间和标题搜索会议纪要。仍然没有时，记录“无可用纪要”，由面试官补人工面试记录。

**远程安装失败**

先检查 GitHub 网络：

```bash
git ls-remote https://github.com/chubbyguan/chubby-recruitment-ops.git HEAD
```
