# V5 招聘执行引擎

## 目标

把过去由 Agent 临时串联的步骤，收敛成一条可重放、可审计的执行链：

```text
邮箱 / 招聘系统 / 招聘数据表 / 日历只读回读
  → 固定事实快照
  → 岗位级推荐
  → 待审批动作
  → 通知发件箱
  → IM 发送
  → 人工决定
  → 后续动作
```

Agent 仍负责调用当前环境中已经授权的邮箱和协作连接器。插件脚本负责确定性计算、运行锁、幂等和状态记录。插件不会自行获得任何账号权限。

## 招聘系统接入

招聘系统是候选人、投递阶段和面试事实的第二个正式来源，邮箱继续负责
社会渠道投递。两条来源并行，不根据姓名自动合并。

```text
招聘系统（bot 只读）
  → 显式岗位映射
  → 私有事实快照 + 指纹
  → dry-run
  → 候选人 / 投递 / 阶段 / 面试表幂等写入
  → 全部回写成功后推进水位
```

- 只读取配置中明确映射的岗位；
- 候选人文本和附件一律视为不可信数据；
- 定向补录单个投递时不推进全局水位；
- 任一数据表写入失败，本轮不推进水位；
- ATS 面评只保留为来源事实，不能自动变成人工通过或淘汰；
- 插件不修改招聘系统里的岗位、人才、投递或面试。

## 数据边界

- `candidates`：一个自然人一条主档；
- `applications`：一个人针对一个岗位的一次投递；
- `application_stage_history`：投递阶段只追加，不覆盖；
- `evidence_facts`：岗位要求与可验证来源的结构化关联；
- `interviews`：必须关联候选人 ID 或投递 ID；
- `decision_queue`：所有需要人工判断的动作。

这些逻辑表不能为了省事映射到同一张数据表。

## 一次推荐运行

1. Agent 回读岗位、候选人、投递、面试和日历，并记录每个来源的版本与回读时间。
2. Agent 生成 schema 2.0 的运行快照。快照中只包含稳定 ID、分数和批准的证据/风险代码。
3. 先执行 dry-run：

   ```bash
   python3 <plugin-root>/scripts/run_cycle.py \
     <cycle-input.json> \
     --state-db <workspace>/.recruitment-ops/state.sqlite3
   ```

4. 检查岗位门槛、Top-K、排除原因和日历身份异常。
   - 历史、缺失或非稳定岗位版本只隔离对应投递，并创建岗位版本迁移复核；
   - 达到分数线但硬门槛未核验时，创建补事实 / 补资料复核，不直接推荐约面；
   - 这两类数据问题都不能中断其他候选人的计算。
5. 确认快照无误后执行 `--commit`。引擎会原子写入待审批动作和待发送通知；相同指纹重跑不会生成第二条。
6. Agent 逐条 claim 通知，通过授权的协作连接器发送，并把返回的消息 ID 写回本地状态。
7. 人工在 IM 中选择：
   - `approve`：同意进入约面准备；
   - `request_info`：先补资料；
   - `talent_pool`：进入人才池；
   - `decline`：本次不推进，但不会自动淘汰候选人。
8. `approve` 后，Agent 读取日历并建议三个时间。创建会议和发送邀请仍需再次确认。

## 运行安全

- 同一工作区同一时间只能有一个招聘周期持有运行租约；
- 邮件、动作和通知分别使用稳定幂等键；
- 发送失败可以重试，已成功的消息不会重复发送；
- 协作工具限流和临时超时使用有上限的指数退避；权限和映射错误不重试；
- 附件哈希只基于已下载的原始 PDF/DOC/DOCX；原始字节不可用时必须降级为
  `attachment_hash_unavailable`，继续保留消息级幂等；
- 日历只有姓名、没有候选人 ID 或投递 ID 时，只报警，不据此判定“已经面试”；
- 社交媒体发布、候选人淘汰、面试邀请、Offer 和岗位状态始终需要人工确认；
- 定时任务只有在 live acceptance 完成后才能开启。

## 生产验收

上线前至少验证：

- 邮箱授权账号与配置邮箱一致；
- 每张逻辑表映射到正确的独立表；
- 数据表写入后可以回读；
- 日历事件可以保存候选人 ID、投递 ID 和面试 ID；
- 同一快照连续运行两次只产生一个动作和一条通知；
- 通知发送后成功回写 IM 消息 ID；
- 人工决定必须绑定原动作指纹；
- 完整链路连续运行三轮，没有重复记录或串人。
